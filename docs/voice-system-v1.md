## 情绪语音强化（v1.6）——「声音平」的定位与修复

**问题**：用户反馈"机器人味"，听感上"开心/难过没什么区别"。

**先定位**（读 CosyVoice 源码，`cosyvoice/cli/frontend.py#L209`）：

```python
def frontend_instruct2(self, tts_text, instruct_text, prompt_wav, ...):
    model_input = self.frontend_zero_shot(tts_text, instruct_text, prompt_wav, ...)
    del model_input['llm_prompt_speech_token']      # ← 参考音频的韵律被丢掉
```

即 **instruct2 通道下参考音频只剩"音色"作用，韵律 100% 由指令文本决定**。两个推论：
① 换参考音频不会带来情绪（所以"录一段更激动的参考音"这条路在 instruct2 下无效）；
② 指令措辞是唯一入口 —— 而旧实现只在拼一句"用…的语气说这句话"。

**再做实验**（`E:\deepseek\tts-tools\`，产物在 `E:\deepseek\cv-out\emo2~emo8`）。
关键方法论：**CosyVoice2 是采样解码，同一条指令每次韵律都不同**（实测同条件时长可差 ±1.4s），
所以每个条件至少跑 3~6 次重复，用 `prosody-analyze.py --agg` 比"均值±标准差"，
并用 `ab-stats.py` 做**双尾 Mann-Whitney U 检验**（n 小、分布不正态，故不用 t 检验），
把差异与采样噪声分开。

| 结论 | 证据 |
|------|------|
| ❌ 指令文案对「开心」**推不动** | 4 种文案（含官方模板 / 强化描述 / `[laughter]`）与"平静自然"地板在语速、音高跨度、力度起伏上**全部落在噪声内**；地板音高跨度 9.34st 甚至比开心的 8.62st 更宽 |
| ✅ **语速旋钮**是开心唯一有效杠杆 | 定案 A/B（n=6/臂，Mann-Whitney）：时长 3.49→2.91s、语速 5.82→6.89 字/s，**p=0.013**。且 5.82×1.15=6.69 ≈ 实测 6.89 → **开心的全部改善来自语速旋钮，与指令文案无关**（这正是不该继续调文案的依据）。1.30x 无额外收益，且会收窄音高跨度（7.51st < 地板 9.75st）→ 取 1.15 |
| ✅ 指令文案对「难过」**有效** | 定案 A/B（speed 两臂都是 1.0，唯一变量是文案）：时长 4.31→5.44s、语速 4.70→3.81 字/s（**p=0.109，趋势**）、**音高跨度 9.06→7.23st（p=0.026，显著）** —— "更慢 + 更平"正是"低沉无力"的正确声学特征 |
| ❌ 细粒度控制符 `[laughter]`/`[breath]` **无效** | `[breath]` 使停顿占比在 19%~37% 双向乱跳，与不加无系统差异（n=3/臂）。已用 tokenizer 确认它们确是特殊 token（各占 1 token、decode 为空、不会被念出来），但**模型不听** → 不采用 |
| ✅ 音色 | `server/assets/voice_prompt.wav` 与官方 `zero_shot_prompt.wav` 字节相同（默认女声，基频 237–289 Hz），用户选定保留 |

> ⚠️ 方法论教训（本项目已因"追噪声"吃过亏）：**每格 1 次比较毫无意义**——同条件时长实测可差 ±1.4s。
> 第一版结论曾写"难过 5.68→3.18 字/s"，那是 **n=3 vs n=1** 的比较，属于过度声称；
> 补到 n=6/臂 后真实值是 4.70→3.81 字/s（趋势级），而**真正显著的是音高跨度**。
> 判据统一为**双尾 Mann-Whitney U，p<0.05**（n 小、分布不正态，故不用 t 检验）。

**根因之二**：`/state` 实测 `calm 0.44 / greed 0.36 / joy 0.17` —— `calm` 常驻最高，
而旧的 `dominantVoiceEmotion` 取"数值最大者"→ **她永远以 calm 发声**，这本身就是"声音平"的成因。

**实现**（v1.6）：

| 组件 | 改动 |
|------|------|
| `src/lib/voiceTone.ts` | 新增 `COSYVOICE_TONES`（每情绪的 mild/strong 指令 + speed）、`cosyVoiceInstruct(emotion, intensity)`、`cosyVoiceSpeed(emotion, intensity)`；指令改走**官方 instruct_list 的模板分布**（`You are a helpful assistant. 请非常X地说一句话。`，见 `common.py#L28`） |
| 同上 | `pickVoiceEmotion(emotions)` → `{emotion, intensity}`：**静息情绪让位** —— 最高者是 calm/neutral 且另有情绪逼近到 `CALM_YIELD_MARGIN`(0.12) 以内时改用它（线上 `calm 0.44 / greed 0.36` 现在会以 greed 发声）；差距更大时仍选 calm（她真的平静） |
| `server/services/cosyVoiceTts.ts` | 双端点：先试带 `speed` 的 `/tts`，遇 **404/405** 回退官方 `/inference_instruct2`（**只丢语速，情绪指令照常生效**），并缓存探测结果；`intensity` 进选项 |
| `scripts`/`tts-tools` | `cosyvoice-server.py` 在官方 app 上**追加** `/tts`（不动官方源码），透出 `speed`/`text_frontend`；`prosody-analyze.py` 量化语速/音高跨度/力度起伏（含 pyin 八度跳变清洗） |
| `src/lib/voiceOutput.ts` / `ChatView.tsx` | `intensity` 随 `pickVoiceEmotion` 一起下发到 `/api/tts` |

**端到端实测**（`E:\deepseek\cv-out\emo7`，走应用自己的 `POST /api/tts`，非直连 TTS 服务）：

```
旧（v1.5 指令 + speed 1.0）vs 新（情绪+强度 → 强化档 + 语速）
```

**诚实的边界**：CosyVoice2 在中文女声 + 中性参考音下推得动的是**时间维度**（语速/停顿/时长），
推不动的是**音高与力度维度** —— 「开心」的音高跨度与力度起伏和"平静"无统计差异，
语速旋钮只能做到"说得快"而非"真的高兴"；「难过」的改善也主要落在"更慢 + 更平"，
而不是"更悲的语调"。若要真正的情绪语调，只有三条路：① 换模型（Chatterbox 等）
② 录一段真人情绪的**同人**参考音（说话人必须一致，否则音色会变）③ 微调。
当前选择是把能推的推到位，并把边界写在文档里，不假装解决了。

### v1.6 补充：「要不要另找情绪参考音频」——对韵律证伪，对音色成立（emo9 + emo10）

用户问过"需不需要找一些参考音频文件"。**结论分两半：对「韵律」不需要，对「音色」需要。**

1. ⚠️ **先更正我自己的过度概括**：`frontend_instruct2` 会 `del llm_prompt_speech_token`，
   参考音频**丢掉的是韵律**；但 `flow_prompt_speech_token` / `prompt_speech_feat` /
   `llm_embedding` / `flow_embedding` **都还在** —— 即**音色（含共鸣位置）完全由参考音频决定**。
   初版写成"外部录音在 instruct2 下做什么都不会发生"，对韵律成立、对音色**不成立**。
2. **参考音频的"韵律"通道只有 `inference_zero_shot` 能用**（它保留该 token）。做了"自举择优"实验：
   生成 8 条候选 → 按 `z(语速)+z(音高跨度)+z(力度起伏)` 择优（冠军 cand4，三维中两维进前二）
   → 用冠军当 prompt 做 zero_shot，把它的韵律"锁"进目标句。
3. **韵律迁移的结果不如现有方案**（同一目标句，n=3 vs 现有 n=6）：

| 方案 | 语速 字/s | 半音跨度 st | 力度起伏 dB | 停顿 % |
|------|----------|------------|------------|--------|
| 现有：强化指令 + 语速 1.15x | **6.90** | 8.27 | 7.08 | 19 |
| zero_shot(择优样本) 锁定 | 4.60 | 8.05 | **8.23** | 35 |
| zero_shot(择优样本) + 语速 1.20x | 5.65 | 8.35 | 7.29 | 36 |

   即：音频级迁移**把"快"丢了**（韵律模板自带更慢的节奏），它唯一的长处（力度起伏 8.23）在加上语速后
   就回落到 7.29，与现有方案没有区别。**花了额外一步（样本库+择优）却换来更慢的语速 → 不划算，未采用。**
4. 想用真人情绪录音还得过"音色会跟着变"这一关（zero_shot 克隆说话人），
   要么放弃默认女声、要么得做"韵律取自 A、音色取自 B"的混合改写 —— 而第 3 点已经说明
   连精心择优的样本都没能超过现有方案，再为它加一层混合改造不成立。

**结论：瓶颈在模型能力，不在素材。** 想真正提升情绪表达，只有换模型/微调这一条路，
不该继续在参考音频上投入。

## 伤心情绪重做（v1.7）—— 按听感反馈把三个维度分开测

**触发**：用户听完 v1.6「新·难过」后给了三条极具体的听感反馈：

> 音高变化：声音偏低，但在情绪激动时会突然向上哽咽或破音。
> 气息不稳：气流断断续续，伴随抽泣声或深吸气。
> 共鸣位置：主要使用胸腔和咽喉共鸣，声音发闷，少用明亮的头腔共鸣。

**先认错**：v1.6 把「半音跨度 p90/p10 收窄」当成"低沉无力"的证据并写进了文档。
但用户描述的真实哭泣是**整体偏低 + 突然向上跳 + 气息断续 + 发闷**，音高**分布形态**完全不同；
一味收窄跨度 = 念得更平更慢，听感上只是拖沓，不像伤心。**指标选对了方向才谈得上优化。**

**先修指标**（`prosody-analyze.py`），把三条反馈各自变成可测量：

| 听感 | 新指标 |
|------|--------|
| 突然向上哽咽/破音 | `f0_jump_up`（连续有声帧间最大上跳，st）、`f0_jumps`（10ms 帧间 >2.0 半音的突变次数） |
| 气息断断续续/抽泣 | `gaps`（内部 ≥60ms 静音段数）、`rough_db`（帧能量差分标准差） |
| 胸腔共鸣/发闷 | `centroid`（频谱重心 Hz）、`hf_ratio`（2–6kHz 能量占比） |

**再分杠杆做实验**（`tts-tools/emotion-sad-test.py` → `emo10`，5 条件 × 6 次重复，
同一句话、speed 全为 1.0，与用户听过的 `new_sad` 可直接对比；Mann-Whitney 双尾 vs 当前实现）：

| 条件 | 语速 | F0中位 | 停顿段 | 频谱重心 | 高频比 | 突变次数 |
|------|------|--------|--------|----------|--------|----------|
| 当前实现（v1.6） | 4.87±0.80 | 283.9±29.7 | 1.33±0.52 | 1705.6±77.8 | 0.217±0.010 | 0.17±0.41 |
| 文本：哽咽/破音/气息断续 | 4.30±0.75 | 255.7±43.2 | **3.00±1.79** (p=0.052) | 1664.9±95.5 | 0.204±0.020 | 0.17±0.41 |
| 文本：胸腔共鸣/发闷 | 4.73±0.63 | **244.7±18.5** (p=0.041) | 2.00±0.63 (p=0.091) | 1652.5±82.5 | 0.205±0.020 | 0.33±0.52 |
| **换暗音色参考音**（指令不变） | 4.41±0.72 | 264.6±27.0 | 1.83±0.75 | **1541.7±91.8 (p=0.004)** | **0.172±0.020 (p=0.004)** | 0.17±0.41 |
| 三者叠加 | 3.57±1.15 (p=0.093) | 250.1±17.8 (p=0.092) | 3.83±3.66 (p=0.052) | 1670.3±66.0 | 0.193±0.020 (p=0.093) | 0.33±0.52 |

**结论（三条反馈，三种命运）**：

1. ✅ **「发闷 / 胸腔共鸣」只能用参考音频做，文本描述做不到**：
   换成"暗音色参考音"（同一说话人自举）后 **频谱重心 −164Hz（p=0.004）、高频比 −21%（p=0.004）**，
   且**语速/音高/停顿全部不变** —— 纯音色改变，零副作用。而文本里写"胸腔共鸣、发闷"时，
   这两个指标**都不显著**（重心 p=0.24、高频比 p=0.49）。→ **音色是参考音频唯一且有效的杠杆。**
2. ✅ **「断续 / 抽泣」可以用文本描述做**：停顿段 1.33 → 3.00（p=0.052），叠加版 → 3.83。
3. ❌ **「突然向上哽咽 / 破音」做不到**：`f0_jump_up` 与 `f0_jumps` 在**所有**变体里都不显著
   （p=0.149~1.000，突变次数始终 ≤0.33）。无论怎么描述，模型都产不出音高骤跳。**这是能力边界。**
4. ⚠️ **叠加有代价**：三者叠加把语速压到 3.57 字/s（p=0.093）——本来就偏慢了，更拖。

**采用的落点**：`sad` 换**暗音色参考音**（`fear` 同理，同为低唤醒负性）。这是本轮唯一
"显著改善 + 零副作用"的一步；"哽咽表述"作为可选项留给用户听感裁定；破音不做承诺。

**测试中要注意的坑**：`prosody-analyze.py --agg` 的组内比较是按 `group` 字段分组的，
若每个条件各占一个 group（如本轮 5 条件 = 5 group），它会找不到基准而静默打印空行 ——
跨条件比较要用 `show-agg.py <dir> <基准条件>`（输出均值±标准差 + Mann-Whitney p 值）。

## 句内情绪转变（v1.8）—— 一句话里的情绪会走，不能整句一个情绪

**触发**（用户原话）："ref_dark 感觉还可以；「我今天有点累，不过看到你的消息就好多了」
这句话前半句应该是疲惫，后半句应该转变为平静吧"。

**问题**：现有实现**整句只施加一个情绪**（`/api/tts` 收一个 `emotion`），
而真实的一句话里情绪会转变。这是能力缺口，不是调参问题。

**新指标**：整句均值**永远测不出**句内转变（前后半会被平均掉）→ 新增
`tts-tools/segment-analyze.py`：按**句内最长的内部停顿**把音频切成前后两半
（切点取自音频本身，所以整句合成与分段拼接都适用），分别算指标再看"后半 − 前半"：
`Δ半音 > 0` = 后半音高上移；`Δ重心 > 0` = 后半音色变亮；停顿前多后少 = 前半断续、后半连贯。

**两条路径对撞**（`tts-tools/emotion-segment-test.py` → `emo11`，4 条件 × 6 次重复；
音色统一用上一轮用户认可的 `ref_dark`，使差异只来自情绪指令）：

| 条件 | Δ半音 | Δ重心 Hz | Δ高频比 | 前半停顿段 | 后半停顿段 | 合成耗时 s | 音频 s |
|------|-------|----------|---------|-----------|-----------|-----------|--------|
| 整句·当前实现（难过强档） | +1.72±1.65 | +146±80 | −0.08±0.06 | 2.00±0.00 | 2.83±0.75 | 10.40±4.05 | 5.49 |
| 整句·**复合指令**（指令里写"前半疲惫后半平静"） | **−1.22±1.66** | +0±148 | −0.02±0.03 | 2.33 | 4.33 | **24.14±16.46** | **10.31** |
| 整句·全疲惫（对照） | **−1.26±1.96** | +118±101 | −0.03±0.03 | 1.50 | 2.67 | 11.75±3.50 | 5.67 |
| **分段合成**（疲惫段 + 平静段拼接） | **+2.85±2.15** | **+396±162** | −0.01±0.04 | **4.00±3.41** | **1.67±1.21** | **11.51±6.02** | 4.60 |

Mann-Whitney（vs 整句当前实现）：

```
分段合成：Δ重心 +250Hz, p=0.009 ✅显著   Δ高频比 +0.06, p=0.041 ✅显著   后半停顿 −1.17, p=0.068 趋势
复合指令：Δ半音 −2.93, p=0.026 显著 —— 但方向是**反的**（后半更低）；Δ重心 p=0.132 不显著
全疲惫  ：Δ半音 −2.97, p=0.009 显著（后半更低）→ 对照有效，说明"不切换"就是这个结果
```

**结论**：

1. ✅ **分段合成是唯一能做出句内情绪转变的路径**：后半音色显著变亮（Δ重心 +396Hz，比当前实现高
   +250Hz，**p=0.009**）、高频比显著提升（**p=0.041**），且**停顿分布反转**（前半 4.0 段 →
   后半 1.7 段：前半断续=疲惫气息，后半连贯=平静），而当前实现是反向的（2.0 → 2.8）。
2. ❌ **一次调用 + 复合指令（路径 A）无效且有害**：模型把 instruct 当**全局条件**，
   做不到句内切换 —— 后半反而更低（Δ半音 −1.22，方向相反），音色毫无变化（Δ重心 +0）。
   更糟的是产出**异常膨胀**（音频 10.31s / 耗时 24s，正常 5s / 10s），
   怀疑它把指令里的引文也念了出来。**已否决。**
3. 🎉 **延迟代价几乎为零**：分段 11.51s vs 整句 10.40s，**只多约 1.1s（+11%）**。
   原本担心是"2 次合成 = 2× 延迟"，实测不是 —— 两个片段都短，总 RTF 相近。

**接线设计原则（尚未落地）**：

- **音色按整句选一次**（用本轮主导情绪对应的参考音），**只有指令与语速按小句变** ——
  同句内换参考音会让音色在句中断裂（本轮实验正是统一用 `ref_dark` 才拿到干净的对比）。
- **按小句切分**：中文标点（，。！？；）切分，**上限 2~3 段**以约束延迟。
- **情绪来源两个候选**：① **引擎状态转变插值**（推荐）：协调器本来就知道"用户这句话之前"与
  "之后"的情绪状态，按小句位置线性取情绪 —— 不需要改 LLM 输出；句子前后半若同情绪则**不切分**
  （零额外代价，安全默认）。② 让 LLM 给每个小句标情绪：语义更准，但要多一次调用、
  且引入编造风险。
- **无转变时不切分**：`Δ主导情绪` 或 `Δvalence` 低于阈值就退回当前单次合成。

## 状态驱动的发声（v1.9）—— 声音是她**此刻状态**的表达，不是给句子贴标签

**触发**（用户原话）："现在要做到的不是把一句话分段，而是理解说这句话所在的状态和情感，
然后自然地表达出来"。这是对 v1.8 思路的纠正：v1.8 在按标点切句、给每段贴情绪标签 ——
**文本驱动的机械流程**；用户要的是**状态驱动**：弧线应当是状态移动的**结果**，不是切句子的**程序**。

**先查代码确认缺口**（这是问题真正的所在）：

| 她的状态 | v1.9 之前是否进到声音 |
|---|---|
| `emotions` 主导标签 / `intensity` | ✅ |
| `taiji.valence` / `arousal` / `expectation` | ❌ 全丢 |
| `internal.mood`（12h 底色） / `internal.rumination`（反刍） | ❌ 全丢 |

后果：**两种完全不同的内心状态，只要主导标签相同，声音一模一样** —— 这就是"机械、没有状态"。

**关键设计（按"通道是否被实测证明有效"分配，不平均用力）**：

| 通道 | 承接什么 | 依据 |
|------|---------|------|
| **参考音音色** | `valence`（负 → 暗音色"发闷/胸腔共鸣"） | 唯一能改共鸣位置的杠杆（emo10：频谱重心 p=0.004） |
| **语速旋钮**（有界 ±） | `arousal` / `expectation` / `mood` / `rumination` | 唯一被证明稳定可控的连续通道（emo8：p=0.013）；且**有界** |
| **指令文本** | **只有情绪基础档** | 见下面的实测教训 |

**⚠️ 本轮最重要的实测教训：状态一旦写进指令，语速会失控（emo12）**

第一版把各维度写成自然语言追加到指令里，结果（n=3，方向一致）：

| 写进指令的短语 | 时长变化 |
|---|---|
| 「今天整体底色就有点沉」 | 3.64s → 5.91s（**+62%**） |
| 「像有件事还没放下」 | 3.64s → 8.31s（**+128%**） |

更糟的是：长指令还让**合成耗时从 8~10s 涨到 30~75s**（近 4 倍），因为更长的 instruct
要更多 prefill/生成。**两件事同时坏掉：不像人、还更慢。**

→ 结论：**时间维度（唤醒度/预期/底色/反刍）一律只走有界的语速旋钮，绝不写进指令**；
文字只留给情绪基础档（它带来的快/慢正是要的效果，且已被 n=6 定案测量过）。
改完之后：时长回到 3.4~5.3s、合成耗时回到 8~10s，全部正常。

**穿透验证（emo12，走应用自己的 `POST /api/tts`，以她**真实状态**为基准做逐维反事实）**：

真实基准：`calm / intensity 0.439 / valence −0.033 / arousal 0.478 / expectation 0.072 / mood 0.024 / rumination streak 1`

| 条件 | speed | timbre | drivers | 频谱重心 Hz | 高频比 |
|------|-------|--------|---------|------------|--------|
| 旧行为（只传标签+强度） | 1 | default | — | 1741 | 0.200 |
| 真实状态（基准） | 1 | default | （空） | **1745** | **0.227** |
| 同上，效价压到 −0.45 | 1 | **dark** | `valence:dark` | **1529** | **0.165** |
| 同上，唤醒度压到 0.1 | **0.94** | default | `arousal:low` | 1654 | 0.215 |
| 同上，底色压到 −0.35 | **0.98** | default | `mood:low` | 1609 | 0.187 |
| 同上，加反刍 streak=5 | **0.95** | default | `rumination` | 1735 | 0.223 |

三个可核对的结论：

1. ✅ **中性状态不"演"**：真实状态（各项都在门槛内）解析出的 speed/timbre/drivers 与**旧行为完全一致**
   —— 说明这一层只在"她确实有状态要说"时才出声，不会无端夸张。
2. ✅ **音色通道可测量**：效价压到 −0.45 → 暗音色，**频谱重心 −216Hz（−12%）、高频比 −27%**，
   三次重复完全不重叠（1529±19 vs 1745±69）。这是本轮最"听得见"的一档。
3. ⚠️ **时间通道很安静，且无法在单样本上验证**：状态带来的语速偏移只有 ±2~6%，
   **小于 CosyVoice 单次采样噪声**（同条件时长可差 ±0.5s），所以单样本测不出。
   它按构造生效（mel 时间插值是确定性缩放，emo8 里 1.15x → 语速 +18%、p=0.013 已验证过该机制），
   但**不要声称"单听就能听出唤醒度的差别"**。

**落点与边界**：

- 新增 `resolveVocalPerformance()`（`src/lib/voiceTone.ts`，纯函数，45 条单测）+
  `buildVoiceState()`（把 EmotionState 抽成快照）+ `voiceStateFromPayload()`（**服务端解析**，只收数字，
  **不接受客户端传的指令文本** —— 否则等于把 TTS 指令通道对任意输入开放）。
- 客户端（`ChatView`）只**原样转发生状态快照**，解释权在服务端（情绪引擎也在那边）。
- 兼容：不传 `voiceState` 的老调用点行为完全不变（有回归测试锁死）。
- 可观测：`GET /state → voice`（`instruct` / `speed` / `timbre` / `drivers`）。
- 保留的能力缺口：**句内状态移动**仍表达不了。CosyVoice2 是全局条件（一段指令/一个语速/一份参考音，
  无逐帧控制），要表达"一句话里状态怎么走"只能 ≥2 次合成拼接（v1.8 已验证效果与代价），
  本次**未接线**。

## 接缝工程（v1.10）—— 让"分两次合成"听起来像一段话

**目标**：v1.8 证明分段合成能做句内情绪转变，但用的是「trim + 固定 120ms 静音 + 硬拼」。
本轮把"接缝"当独立问题，逐个杠杆验证（`tts-tools/seam-test.py` + `seam-analyze.py` → `emo14`）。

**先把"接缝"变成可测量的**（三个指标，都相对"单次生成"这一档）：

| 指标 | 含义 |
|------|------|
| `seam_mfcc_ratio` | 停顿**两条边**上的最大帧间 MFCC 距离 ÷ 全句帧间距离 p95。≈1 = 接缝处和正常语音帧间变化同量级 |
| `pause_ms` | 逗号停顿实际长度 —— 人工间隙是否接近模型的天然逗号停顿 |
| `f0_step_st` / `level_mismatch_db` | 停顿前后的音高跳 / 两侧有声部分能量差 |

⚠️ **两个自己踩的坑（都修了，值得记下来）**：
1. **指标不公平**：第一版把"接缝帧"取成 seg1 结束的位置，而单次生成取的是**停顿中心** ——
   前者落在"语音→静音"的边上、后者落在静音里，于是单次生成算出 0.00、拼接算出 1.3~1.7，
   **根本不是同一个量在比**。改成统一取停顿的两条边后才可比。
2. **交叉淡化实现有 bug**：第一版在交叉前又插了一段 gap，导致 a 的语音尾巴被挪到静音之后、
   与 b 的头部叠在一起（两段语音重叠），那版 C 的指标反而更差。修正为"直接交叉两段 trim 后的
   近静音边缘、不额外插静音"。

**结果（n=6；`E_single` 是无接缝的参照尺子 n=4）**：

| 条件 | 逗号停顿 ms | 接缝比值 | 音高跳 st | 响度差 dB |
|------|------------|---------|-----------|-----------|
| **单次生成（无接缝参照）** | **818** | **0.59** | 4.15 | **0.77** |
| A 现状：trim + 120ms 硬拼（v1.8） | 358 | 1.28 | 6.05 | 2.85 |
| B A + 两段响度对齐 | 332 | 1.35 | 4.43 | 2.56 |
| C B + 等功率交叉淡化（不插静音） | 192 | **0.88** | 4.07 | 2.66 |
| F B + 间隙加长到 260ms | 430 | 1.36 | 4.43 | 2.56 |
| D **后段以【前段音频】为参考音** | **662** | **0.94** | 5.45 | 3.29 |

**三个结论，两个是我的假设被证伪**：

1. ✅ **天然的逗号停顿约 818ms，而我们人工只用 120ms** —— 差 6.8 倍。
   这是一个稳定、可直接用的发现：**我们的拼接在逗号处明显偏赶**（实测 A 的停顿 358ms，仍不到天然的一半）。
2. ❌ **"响度对齐"被证伪**：比值 1.28→1.35、响度差反而 2.85→2.56（噪声级）。TTS 同源同参考音，
   两段响度本来就齐，**接缝不是响度问题**。
3. ❌ **"单纯加长间隙"被证伪**：F 把间隙加到 260ms，比值仍 1.36。
   → 说明问题不在时长，而在**两段衔接处的频谱/韵律不连续**。
4. ⚠️ **交叉淡化（C）确实把频谱突变降到 0.88（最接近天然的 0.59），但把逗号吃到 192ms**，
   还有 1/4 的样本直接没了停顿 —— 是**拿节奏换平滑**，不划算。
5. ⚠️ **D（后段拿前段当参考音）方向是对的**（比值 1.28→0.94、停顿 358→662ms 双双朝天然靠），
   机制也正确（`frontend_instruct2` 保留了 `flow_prompt_speech_token`/`prompt_speech_feat`，
   后段的 flow/声码器是从前段结尾的 mel 接着走的）。
   **但在 n=6 下未达统计显著**（比值 Δ=0.34，合并 SD≈0.58，2SD≈1.17；停顿 Δ=304ms vs 2SD≈602ms）。
   n=4 时看着像 0.73 vs 1.36 的"明显改善"，补到 n=6 就缩到 0.94 vs 1.28 ——
   **又一次"小样本看着很美"的教训**。要检出这个量级的差异需要 n≈30。

**采用的落点**：D 的成本是**零**（同样是 2 次合成，只是把 seg1 的音频当 seg2 的参考音），
方向也一致，故作为弧线的默认做法；同时把人工间隙向天然停顿靠拢。
但**不宣称它已被统计证明** —— 最终判据是听感。

## 句内状态弧线接线（v1.11）—— 从"分段"改成"状态在走"

**用户听感裁定**（emo14）："A 的两者感情衔接的 gap 有点大；`D_chain_r6` 比较自然一点"。
注意 A 的逗号停顿只有 358ms、D_chain 是 662ms（他挑中的 r6 是 980ms，天然 818ms）——
**耳朵和数据指向同一件事**：A 像两段被硬拼起来，D 因为 flow 侧延续而像一口气说完。

**落地形态**（不是"按标点切句贴标签"，而是"状态在走"）：

| 环节 | 做法 |
|------|------|
| 状态来源 | `before` = **用户这句话之前**她的状态（服务端在跑这一轮前**冻结**成纯数据）；`after` = 本轮之后的 |
| 要不要切 | `shouldUseVoiceArc()`：主导情绪换人 **或** |Δvalence| ≥ 0.12 才切；否则单次合成（**零额外代价**） |
| 每段什么语气 | `buildVoiceArc()` 在 before→after 之间按位置插值**九情向量**，再取主导 —— 交接点是算出来的 |
| 怎么合成 | 第 1 段用情绪参考音；第 k 段用**第 k-1 段的音频**当参考音（v1.10 实测的 D 做法） |
| 逗号停顿 | **只 trim 最外侧**，内侧静音保留；再补 `ARC_MIN_GAP_MS=450` |
| 失败处理 | 任一段失败 → 回退单次整句（绝不因为语音把聊天弄坏） |

**接线时实测踩到的三个坑（都已修）**：

1. **五处闭环缺口**：`voiceStateFromPayload` 没有解析九情向量 → 弧线只能单侧插值，
   末段九情全归 0。已补上（只收白名单键 + 有限数字 + 钳制到 [-1,1]）。
2. **潜伏 bug（v1.6 就有）**：`pickVoiceEmotion` 对**全零向量**不过滤零值，
   `reduce` 会随手挑到第一个键 → 报出"`sad intensity=0`"这种假主导情绪。
   已改为只收非零值，全零 → `neutral`（有回归测试）。
3. **间隙标定**：第一版补 220ms 且把**内侧静音也掐掉** → 成品逗号停顿只有 317ms，
   比用户认可的那版（662ms）还赶。查清机理：**整句生成时模型在逗号处有 760~818ms 停顿，
   但单独生成一个小句只贡献 ~270ms**（看不到后文，不会拖长）。故把间隙标定为 **450ms**
   （450 + 模型自身 ~270 ≈ 720ms，与天然同量级）。

**接线后端到端实测**（`emo15`，走应用自己的 `/api/tts`）：

| | 逗号停顿 | 接缝 MFCC 比值 | 合成耗时 | 音频时长 |
|---|---|---|---|---|
| 单次整句（只传 after） | 610ms | 1.69 | 8.6~9.6s | 3.8~4.4s |
| **句内弧线（before+after）** | **803ms** | 1.22 | 10.2~16.0s | 3.9~7.2s |

→ 弧线的逗号停顿 **803ms ≈ 单次生成的天然停顿（760~818ms）**，接缝比值也更低。
延迟代价：2 次合成，约 +20~80%（视片段长度）。

**可观测**：`GET /state → voiceArc`（`used` / `clauses` / `timbreUsed` / 每段的 emotion/intensity/valence/arousal/speed，
以及不切分时的 `reason`）。**`timbreUsed` 只由第一段决定** —— 链式参考音会让后段继承前段音色，
所以"每段各自 timbre"是无效的，这一点必须写在可观测里免得误读。

**仍未做**：间隙 450ms 是按单句标定的常数，不是按语速自适应。

**前端消费（同日补齐）**：`SettingsView` 新增**发声诊断**面板（`VoiceDiagnostics`）——
`/state → voice`/`voiceArc` 此前**没有任何界面消费**，只能翻接口。现在展示：
指令、语速、音色（人话）、**状态驱动来源（drivers）**、以及**这次有没有走句内弧线**
（起/落两段的情绪·强度·效价·唤醒·语速 + 分句，或未分段的原因）。每 10s 自动刷新、只读。
展示逻辑放在 `src/lib/voiceTone.ts` 的 `describeVoicePerformance()`（纯函数，6 条单测），
不在 JSX 里 —— 这样"怎么读这次发声"是可单测、可复用到聊天页的。

### v1.11 补充：段数上限与**边际延迟实测**（emo16）

问题：段数该不该限制？限几段？"段数按感情自然调整"听起来对，但**每段就是一次独立合成**，
而播放要等合成完成 —— 所以段数直接乘在用户等待上。这一段把代价量出来。

**方法**：同一句话（3 个小句）固定不变，只改段数上限 1/2/3（`arcMaxSegments`），
三臂**轮转交错**执行；每轮取「本臂耗时 ÷ 本轮 1 段耗时」做配对比较（抵消机器漂移）。
端点走应用自己的 `POST /api/tts`（`scripts/measure-arc-latency.ts`）。
分析脚本从**服务日志**还原每次调用自身的耗时与音频秒数（`arc-latency-analyze.py`）。

文本：「我今天有点累，不过听到你的声音就好多了，一下子又有力气了。」

| 轮 | 1 段 T/a/rtf | 2 段 T/a/rtf | 3 段 T/a/rtf | 轮内 rtf 极差 |
|---|---|---|---|---|
| 1 | 14.8s/6.76s/2.18 | 14.5s/5.98s/2.42 | 17.9s/7.10s/2.52 | 1.65 |
| 2 | 13.9s/6.60s/2.10 | 15.7s/6.28s/2.51 | 23.8s/8.98s/2.65 | 1.66 |
| 3 | 15.5s/5.68s/2.72 | 14.3s/4.82s/2.97 | 19.6s/6.54s/3.00 | 1.86 |
| 4 | 25.3s/5.84s/4.33 | 30.8s/6.54s/4.71 | 19.1s/6.12s/3.12 | 2.21 |
| 5 | 12.8s/6.40s/2.00 | 38.4s/8.84s/4.35 | 41.0s/8.52s/4.82 | 2.76 |
| 6 | 24.5s/5.46s/4.49 | 35.8s/7.42s/4.82 | 36.2s/6.84s/5.30 | 1.32 |

配对结果（每轮各自除以本轮 1 段）：

- **2 段/1 段：中位 1.18×**（逐轮 0.98 / 1.13 / 0.93 / 1.22 / 3.00 / 1.46）
- **3 段/1 段：中位 1.37×**（逐轮 1.21 / 1.72 / 1.27 / 0.76 / 3.21 / 1.48）

机理模型 `T = a·r + n·f`（a = 音频秒、n = 段数）：由轮内比值反解 **f/r 中位 0.81**
（逐轮 0.39~1.83），整句实测 r ≈ 2.97 秒/音频秒
→ **每次调用的固定开销 f ≈ 2.4 秒 ⇒ 每多切一段 ≈ +2.4s**（健康态 r≈2.2 时约 +1.8s），
再加该段多出来的边界静音（≈0.4×r，约 +1s）。

**三个结论**：

1. **切段的代价远小于"N 倍"**：同一句话，段数只改变"分几次生成"，不改变总字数；
   实测总音频只从 6.12s 涨到 7.35s（段边界静音），所以 3 段是 **1.37×** 而不是 3×。
   绝对量：健康态单次整句 ~15s → 3 段约 **+4s**。
2. **真正的延迟风险不是段数，是这台机器的 TTS 吞吐**：同一次 6 分钟测量里，
   单次整句从 13.9s 漂到 25.3s（rtf 2.10 → 4.49），**波动比 3 段的全部代价还大**；
   轮内 45 秒的极差就有 1.65~2.76×。所以段数上限该按"能否稳定合成"来定，
   而不是把它当成延迟的主要闸门。
3. **因此上限设为 3（`VOICE_ARC_HARD_MAX`），实际段数**由感情算 → 见下一节 v1.12。
   可用 `COSYVOICE_ARC_MAX_SEGMENTS` 环境变量或请求体 `arcMaxSegments` 覆盖
   （服务端钳制到 [1,3]，**不接受无界输入**——段数是延迟乘数）。

## 段数由感情决定（v1.12）——「上限 3，实际几段听感情的」

**用户裁定**（听完 emo16 的 1/2/3 段对照）："两段好一点，但是存在三段的感情变化，占少数，
所以上限为 3 吧，然后具体的根据角色感情自然流露。"

于是把段数从**配置**改成**算出来的**：

| 层 | 是什么 | 谁定 |
|---|---|---|
| `VOICE_ARC_HARD_MAX = 3` | 硬上限（延迟护栏，实测每多一段 ≈ +2.4s） | 常量 |
| `resolveArcMaxSegments()` | 本次**允许**的上限（env / 请求体可覆盖，钳制 [1,3]） | 配置 |
| **`resolveArcSegments()`** | **这一句实际切几段** | **感情** |

判据（`hasIndependentMiddle()`）：把 before→after 插值到中点，取**中段实际会发出的那个情绪**
（用的是与生成时**完全同一个** `pickVoiceEmotion`），要求它

1. **既不是起点情绪、也不是终点情绪** —— 否则第 3 段只是把第 1 段再念一遍；
2. **赢得干净**：中段 ≥ 前后两种情绪在中点的值 × `VOICE_ARC_MID_MARGIN`(1.15)
   —— 线性插值的中点常是几个情绪的胶着状态，胶着时判出的主导是噪声，不该据此切段
   （与 v1.15「无信号即无误差」同一条原则）。

```ts
sad .55/.10/.02  →  calm .12/.40/.15    中点仍是 sad      → 2 段（用户听着更好）
sad .50/love .10 →  joy .40/love .50    中点被 love 接管  → 3 段（三段各有话说）
sad .50/anger.26 →  joy .50/anger.26    中点胶着(仅+4%)   → 2 段（不切）
```

**接线时的一个真 bug（被单测当场逮到）**：`hasIndependentMiddle` 第一版按**原始数值排名**
挑中点情绪，而真正生成分段的 `buildVoiceArc` 用的是 `pickVoiceEmotion`（带 `CALM_YIELD_MARGIN`
让位规则）—— 于是出现"判定说切 3 段、中段却发出起点情绪"的不一致。
修法：**判定与生成共用同一个选取函数**，`middleVoiceEmotion()` 也走它，三处结论永远一致。
（反例已进单测：中点 calm 只领先 0.075 < 0.12 时，calm 会按让位规则退给起点情绪 → 判 2 段。）

**可观测**：`/state → voiceArc` 新增 `segments`（实际段数）与 `segmentReason`（人话理由，
如"中段仍是「sad」和开头同一种情绪 → 2 段（第 3 段只会把它再念一遍）"），
设置页的发声诊断面板会显示这一行 —— 需求是"段数根据感情自然调整"，
那就必须能回答"这一轮为什么是 2 段不是 3 段"。

**仍未做**：判据只用了"中点"这一个时间点。真正的三相位模型（12h 心情底色 → 本轮用户事件
→ 落定）还没建：`mood` 目前只进语速，没有参与"有几个相位"的判断。
