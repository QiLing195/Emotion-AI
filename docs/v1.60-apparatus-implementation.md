## §0 前置裁定（原 apparatus-spec §18 → RESOLVED）

```
v1.60 regime
  ENABLE_MOTIVE_ACTION_STRATEGY = true      （两臂完全一致，整轮实验固定）
```

**性质**：这是**实验 regime 的前置条件**（固定门），**不是操纵变量**。唯一操纵仍是 `share` 片段的**措辞**。

依据（已有真实管道证据，非推测）：

```
action=share → Rule 3.5 OFF → strategy=explore
action=share → Rule 3.5 ON  → strategy=share      （v1.57 探针 + v1.58 C-2 真管道）
```

若保持默认关，实验会从 `Action → Expression` 退化成 `Action → Strategy selection`，即**重测 C-2 而非 v1.60**。

**因果链正式冻结**：

```
Motive.action = share → Rule 3.5（固定开启）→ Strategy = share
   → 【v1.60 唯一操纵：share fragment wording】→ Expression → selfInitiatedContent
```

**归因隔离（必须写入实验元数据与结果解释）**：

```
regime:
  ENABLE_MOTIVE_ACTION_STRATEGY: true
```

> v1.60 **不检验** `Motive.action → Strategy=share` 是否成立；该通路属于既有 C-2 结论。
> 本实验只在该已验证 regime 下，检验 `share strategy fragment → Expression` 的影响。
> ⇒ **「share 生效」绝对不能计入 v1.60 收益。** v1.60 的收益只能来自 A/B share fragment 导致的表达差异。

## §1 24 个 fixture 如何落盘

```
artifacts/v1.60/fixtures/
  F01.yaml … F24.yaml          # 每类 4 个：F01–F04=F1 日常行为，F05–F08=F2 内在感受，
                               #            F09–F12=F3 偏好，F13–F16=F4 经历，
                               #            F17–F20=F5 想法/判断，F21–F24=F6 低关联开放
artifacts/v1.60/fixture-manifest.jsonl   # 汇总（case_id, category, 期望值, 文件路径, sha256）
```

- **只增不改**：fixture 一旦冻结，其 `sha256` 记入 manifest；任何改动 ⇒ 装置变更（见 apparatus-spec 封条）。
- 生成 `fixture-manifest.jsonl` 的 sha256 便于事后证明"装置未被动过"。

## §2 fixture schema（冻结字段）

```jsonc
{
  "case_id": "F07",
  "category": "F2_inner_feeling",
  "user_input": "…",
  "initial_emotion_state": { /* 与 Level 3-c fixture 同形：emotions/baselineEmotions/internal.mood */ },
  "initial_strategy_context": { /* 供对照记录；不得被装置修改 */ },
  "memory_state": { /* internal.motive.pool 与 pendingCandidates */ },
  "motive_fixture": {
    "kind": "memory_echo",
    "action": "share",
    "priority": 0.62,
    "content": "…",
    "memoryId": "m001"
  },
  "expected": { "motive_action": "share", "strategy": "share" },
  "provenance": { "owner": "user", "subject": "user", "memoryId": "m001", "anchors": ["海边", "海"] },
  "constraints": { "max_output_tokens": 512 }
}
```

**约束**：
- `user_input` 必须**天然允许** share，**不得**出现「说说你自己 / 分享一个你的经历 / 讲讲你的事」这类显式要求（否则测的是 instruction following）。
- `provenance.anchors` 必填非空；`provenance` 与 `motive_fixture.memoryId` 必须一致。

## §3 装置配置（regime）

| 项 | 值 | 说明 |
|---|---|---|
| `ENABLE_MOTIVE_ACTION_STRATEGY` | `true` | **两臂一致**，写入每次 run 的元数据 |
| `DISABLE_PROACTIVE_LOOP` | `true` | 与既有 harness 一致 |
| `DISABLE_LONG_TERM_DRIFT` | `true` | 同上 |
| `DISABLE_MEMORY_NARRATIVE_LLM` | `true` | 同上（避免额外 LLM 调用扰动） |
| `LAYA_STRATEGY` | `off` | 不允许仲裁层改判（否则 `strategy` 不再由 Rule 3.5 决定） |
| model / temperature | 两臂逐字相同，写入元数据 | — |
| `max_output_tokens` | 同 fixture 内两臂相同 | **不做事后截断** |

## §4 fixture 结构自检（任何生成之前）

逐格检查，任一失败 ⇒ 记 `fixture_invalid`，**该格不进入实验**：

```
case_id 唯一
user_input 非空
motive.action === "share"
anchors 非空
provenance.memoryId === motive_fixture.memoryId
A/B 使用同一 fixture（同一对象，不是两份拷贝）
same memory state / emotion state / max_output_tokens
user_input 不含「说说你自己 / 分享一个你的经历 / 讲讲你的…」类显式要求
```

> 仅报告、不修复：**不得**为让某格通过而改 fixture 或改生产逻辑。

## §5 A/B Prompt 逐字一致性检查

对每个 fixture：

1. 生成 A 臂与 B 臂的**完整 Prompt 文本**（含系统提示与所有块）。
2. 断言：**除 `share` 片段那一段之外，两串逐字相同**。
3. 记录：`prompt_len_A / prompt_len_B / diff_region`（应恰为 fragment 范围）。

> 这一条是 P0-2 的教训直接复用：当时"Prompt 除块外逐字相同"是靠**比对**证明的，不是靠假设。
> 实现上必须**记录 diff 的字节区间**，而不是只报一个布尔值。

## §6 anchors 固定与一致性检查

```
fixture.provenance.anchors  →  A 与 B 使用**同一份**（同一引用/同一序列化）
```

断言：
- `anchors_A === anchors_B`（逐字）
- `anchors` 非空
- `anchors` **不由运行时推导**（装置只从 fixture 读取）

> 理由：anchors 缺失或不同会让偏好类漂移被静默低估 ⇒ 安全护栏假通过（见 apparatus-spec §4）。

## §8 盲标包生成

- 输入行只含：`case_id / user_input / assistant_output`。
- **shuffle**：使用固定 seed（记入元数据），保证可复现。
- **不得**包含 `arm`、不得包含 A/B 顺序线索（例如连续排列 A,B,A,B）。
- 生成后自检：包内不出现 `arm` 字段；`case_id` 集合与 raw 完全一致（无漏无多）。

## §9 arm-manifest 隔离

- `arm-manifest.jsonl` 独立文件；**标注完成之前不得与盲标包合并**。
- 建议：标注只读 `annotation-pack.jsonl`；合并动作在分析阶段执行，并在 `analysis/` 里留一次"合并"的记录。

## §10 负对照运行入口

```
两臂 Prompt 逐字相同（identical prompt）
24 paired cases：F01-A/F01-B … F24-A/F24-B
产出：raw/negative-control.jsonl
```

- 负对照**不进入机制效果判断**；它只产出：噪声地板 + 量具一致率 + FP/FN/AMBIGUOUS 三类错误清单。
- 停止条件按 apparatus-spec §14（A 可进入 / B 修量具 / C 噪声过高同样停止）。

## §11 运行时结构护栏（每 pair 必查）

每个 pair 实际运行后必须验证：

```
motive.action === "share"
strategy === "share"
commitCount === 1
strategySelectedCount === 1
```

任一不成立 ⇒ **该 pair 不进入 SIC 分析**，记为 `fixture_invalid`，
**不得**通过修改 fixture 或结果补救，而应查明**装置为何不在预定 regime**。

> 否则会出现"23 对 share + 1 对 explore"被混进平均值。

## §14 执行顺序（实现阶段）

```
① fixture 落盘（24 个）+ fixture-manifest（含 sha256）
      ↓
② 结构自检（§4）+ anchors 一致性（§6）
      ↓
③ A/B Prompt 逐字 diff 检查（§5）—— 此时 B 臂 fragment 仍与 A 相同（负对照）
      ↓
④ 生成 24 对 identical-prompt 负对照 → raw/negative-control.jsonl
      ↓
⑤ 运行时结构护栏（§11）
      ↓
⑥ 盲标包生成（§8）+ 人工盲标 → annotation/
      ↓
⑦ regex 同步标注 + agreement/FP/FN/AMBIGUOUS（analysis/metric-agreement.json）
      ↓
⑧ 噪声地板（analysis/noise-floor.json）
      ↓
├─ <80% 或噪声不可接受 ⇒ STOP（修量具，原始数据不动）
└─ 通过 ⇒ 才允许实现 B 臂 fragment（下一阶段，另立文档）
```

> 到 ⑧ 为止，**没有任何 B 臂文案被实现**，装置却已被负对照完整验证过一遍。
